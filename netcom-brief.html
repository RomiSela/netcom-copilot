Goals and success metrics

Goal: customers get their problem solved on the first call, and fewer of them leave. We get there by helping agents follow procedure during the call. The north-star metric is the share of customers who call again within 7 days.

Pilot with one team. The other three teams keep working as today and serve as the control group. This shows that the change comes from the Co-Pilot and not from the season or the call volume, limits the risk while the tool is new, and lets us fix what slows agents down before a wider rollout.

If the pilot team meets the 3-month targets, we roll the Co-Pilot out to all teams and set the metrics for center-wide use.

The flow

Two users, two jobs: the agent resolves one call at a time; the contact-center manager makes sure the whole center follows procedure.

Agent: handling a call

  1. Answers a call without knowing who is calling; the customer card opens once they say their ID.
  2. Handles the request with the procedure for that call type shown at the right moment.
  3. Closes and logs the call: checks the AI draft, fixes what is wrong, saves.
  4. Between calls, looks up past calls and checks their results against the team.

Contact-center manager: running the center

  1. Checks the status: are satisfaction, repeat calls and retention offers getting better or worse?
  2. Finds where it hurts most, with a suggested action.
  3. Drills into a team, an agent or a call to see where procedure broke.
  4. Acts: a team briefing, coaching, or a process change.

Key product decisions

  1. Guidance inside the transcript, at the moment it is needed. During a call the agent reads the conversation, so the procedure reminder appears right after the sentence that triggered it.
  2. Answer first, identify from speech. Calls arrive before anyone knows the caller. The Co-Pilot hears the ID number and opens the customer card, and the number is never read back.
  3. The AI drafts the CRM log; the agent approves it. Logging is mandatory and typed by hand today. The agent checks the draft, keeps their own notes, and saves in one click.
  4. The manager page is ordered by business impact. Status first, then the three problems, each with one number, one chart and one suggested action. Details open on demand.
  5. Coaching, not ranking. Agents see their own results against the team average; the manager sees every agent. Each score shows how many surveys it rests on.

Risks to watch

  • Alert fatigue. Too many prompts and agents stop reading them. Alerts appear only at procedure moments, and the pilot tracks how often agents act on them.
  • Hebrew speech-to-text accuracy, especially for spoken numbers such as ID numbers. The agent confirms the match before the card opens and can always type the ID.
  • Privacy. Calls are recorded and ID numbers are spoken. The ID is masked on screen and never read back; transcripts should follow the same retention rules as recordings.

Build approach and tooling

Approach. Data first: I analysed the September call log to see where repeat calls and lost customers come from, then read the transcripts and the policy against those numbers to find the cause. Then I designed the two user journeys and built the prototype in short rounds, checking each version in a browser.

Tools. Claude Code for analysis, code and testing · Python for the data analysis · React, Tailwind CSS, Lucide icons and Recharts for the interface · claude.ai Artifacts for hosting and for saving CRM logs.

Real vs. mocked. The interface is real. Netcom’s systems (CRM, speech-to-text, phone system, AI engine) sit behind one API layer that follows integration_spec.md, with mock servers that add realistic latency and the spec’s errors. A real system can replace each mock without changing the screens. The AI analysis of the 6 sample calls is written in advance, and live calls are scripted.
